# AI_MIDI 代码审查报告（2026-09-05）

## 概述

对全仓库做了全面 bug 与设计漏洞审查：Go 后端（`main.go`、`internal/` 全部 10 个包）、C++ 音频引擎（`engine/Source` 全部源码）、前端（`frontend/js` 全部 17 个模块），并交叉核对了 Go↔引擎 IPC 协议两端、前端↔Go API 的一致性。

**结论**：未发现命令注入、XSS、API Key 泄漏路径；路径穿越主防线（SafeJoin/ResolveMidiPath/isSubPathFS）与引擎进程三层回收（协议优雅退出 → killProcess → Windows Job Object）扎实。共确认 **高危 11 项、中危 25 项、低危 25+ 项**。

**本轮修复**：全部高危 + 有实际用户影响的中危（26 项，含 C++ 引擎 4 处，已重编 `bin/aimidi-engine.exe` 并通过 IPC 冒烟）。低危记录在案，暂不修。

状态图例：✅ 已修复（含测试）｜📋 记录不修（含原因）

## 一、高危（全部 ✅ 已修复）

### H1. 撤回快照与活数据共享底层数组 → 恢复出损坏历史
- 位置：`internal/server/handler_project.go`（messages/edit 与 messages/undo-edit 的 PendingEdit）
- 问题：快照存 `st.FullHistory` 浅引用后截断 `[:histIdx+1]`；后续流式 append 原地覆写底层数组槽位，「撤回修改」恢复出旧前缀+新消息的混合体，被截消息永久丢失。`chat_display` 中的嵌套 map 同样被 pipeline 就地修改穿透。UndoEntry.Files 亦同。
- 修复：`chat.CloneHistory/CloneDisplay` 深拷贝（`internal/chat/session.go`）；PendingEdit、全部 4 处 UndoEntry 压栈、save_notes 改拷贝后替换。测试：`internal/chat/clone_test.go`。

### H2. tasks.json / history.json 损坏被静默清空重写
- 位置：`internal/tasks/registry.go`（loadTasks）、`internal/project/history.go`（LoadHistory/LoadEditHistory）
- 问题：unmarshal 失败 → 空列表 → 任意一次保存把原件（可能半截可恢复）替换为空内容。任务面板全空 / 聊天历史丢失。
- 修复：损坏先备份为 `*.corrupt-<时间戳>-<pid>-<序号>` + slog.Error（对齐 index.json 既有策略）；tasks.json 损坏期间 `saveLocked` 拒绝落盘。测试：`registry_corrupt_test.go`、`history_corrupt_test.go`。

### H3. delete_midi 无条件报「成功删除」
- 位置：`internal/mcp/executor.go`（deleteWithMirror）
- 问题：`os.Remove` 错误被忽略；Windows 文件被播放器/DAW 占用时工具对 LLM 谎报成功，清单/聊天记录照常更新，与磁盘永久脱节。
- 修复：deleteWithMirror 返回 error，失败如实返回「文件可能正被占用」；镜像删除失败记日志。

### H4. bounce 固定 30s 超时杀掉长渲染
- 位置：`internal/engine/supervisor.go`（Supervisor.Bounce）
- 问题：引擎允许渲染最长 600s 音频；超时 → `markDead` 会话判死 → supervisor 重启并 `killProcess` 杀掉正在写 WAV 的引擎。
- 修复：`estimateBounceTimeout` 按引擎 computeBeats 同款逻辑（notes[].end / clips[].start+length / tracks[].clips[] 展开）估算音频时长，超时 = 2×音频时长 + 60s（下限 30s、上限 20min）。测试：`supervisor_bounce_test.go`。

### H5. 引擎 bounce 阻塞管道线程 → 渲染期间 IPC 全瘫痪
- 位置：`engine/Source/Main.cpp`（handleMethod 的 "bounce" 分支）
- 问题：bounce 在管道读线程同步执行（scheduleSamples 已修成 callAsync，此处漏改），渲染期间 MIDI 帧/ping/timecode 全部排队。
- 修复：对齐 scheduleSamples 的 `MessageManager::callAsync` 模式。

### H6. 音频实时线程每块深拷贝调度表 → 周期性撕裂
- 位置：`engine/Source/Audio/EngineAudioDevice.h/.cpp`（audioDeviceIOCallbackWithContext）
- 问题：每个音频块（~5.8ms@512）在实时线程深拷贝整个 `scheduledSamples_`（含逐个 juce::String 分配），违反「回调内零分配」纪律；`hasScheduledSamples` 还存在无锁读（UB）。
- 修复：调度表改 `shared_ptr<const vector>` 发布/读取——写方整表构建后交换指针，音频回调只拷贝指针（引用计数原子增，纳秒级临界区），全部 6 处使用点同步改造。

### H7. SSE 客户端停滞可冻结整个项目
- 位置：`internal/main.go`（http.ListenAndServe 零超时）+ `internal/server/handler_chat.go`（同步 Fprint 无写超时）+ `internal/chat/pipeline.go`（持 fl 锁调用 onEvent）
- 问题：浏览器后台节流/僵死连接 → TCP 发送缓冲填满 → Fprint 无限期阻塞 → fl 永不释放 → 该项目全部请求挂起，无法自愈。
- 修复：① http.Server 设 ReadHeaderTimeout/IdleTimeout（不设 WriteTimeout 以免掐断 SSE 长下行）；② SSE 回调每写前 `SetWriteDeadline(15s)`；③ pipeline 全部 12 处 onEvent 改为「锁内快照（SnapshotDisplay/SnapshotMidiFiles）、锁外 emit」。

### H8. 上传/JSON 接口无请求体上限
- 位置：`internal/server/handler_midi.go`（ParseMultipartForm 只是内存阈值）、全部 JSON handler
- 问题：任意本机进程 POST 超大 body 可填满临时目录 / 触发无界内存分配。
- 修复：`router.go` 统一中间件 `requestLimitFor`：默认 2MB；`/api/parse` 64MB、`/api/audio/` 48MB、`/api/arrangement/` 8MB、项目文件上传 256MB（与各 handler 内部既有上限取交集）。

### H9. 引擎推送帧无专职读者
- 位置：`internal/engine/client.go`（Events() 通道零消费者；timecode 仅在请求事务内被顺带消费）
- 问题：架构上「半双工事务模型承载全双工流量」，空闲期推送帧堆积在管道内核缓冲，极端时反压音频线程。
- 状态：📋 **记录不修**。实测冒烟中 timecode 推送（20ms/帧）在 64KB 管道缓冲下正常流动，且前端 50ms 轮询持续产生读事务；真正修复需要协议级改造（专职 reader goroutine 或引擎侧降频），风险收益比不划算。建议后续迭代再议。

### H10. 引擎命名管道无鉴权 + 引擎侧零路径校验
- 位置：`engine/Source/Ipc/PipeServer.cpp`（默认 DACL）、`engine/Source/Main.cpp`（loadSoundFont/bounce 的 path 不校验）
- 问题：本机任意进程可连管道令引擎读写任意路径；Go 侧白名单只保护自家调用方。
- 状态：📋 **记录不修**。本机单用户桌面应用，管道名含 PID、`PIPE_REJECT_REMOTE_CLIENTS` 已挡远程；纵深防御属协议迭代（建议引擎侧复用 isSubPath 校验），本轮不动。

### H11. 多会话场景互杀引擎
- 位置：`internal/engine/cleanup_windows.go` + `main.go`（`Local\` 前缀互斥体 + 全盘查杀 aimidi-engine.exe）
- 问题：Windows 多终端会话（快速用户切换/RDP）各跑一个实例时，后启动实例的清场会杀掉对方合法引擎，形成互相杀循环。
- 状态：📋 **记录不修**。单用户桌面场景不触发；彻底修复需把互斥体改 `Global\` 命名空间 + 清场范围限定会话，涉及产品语义（是否允许双开）。

## 四、架构层面建议（后续迭代主题）

1. **「快照」语义纪律**：凡「存起来以后再恢复」的数据（UndoEntry、PendingEdit、removalInfo）必须显式深拷贝。本轮已统一 CloneHistory/CloneDisplay/SnapshotMidiFiles，建议后续新增快照点强制沿用。
2. **锁内只动内存**：fl 内做磁盘 I/O（SaveHistory）与网络写（SSE，已修）都会把局部阻塞放大成项目假死。I/O 移到锁外快照上是下一轮方向。
3. **超时/重试预算集中化**：Go 侧 30s/15s/5s 常数散落，与引擎最坏耗时（600s 渲染、大素材解码）无协商机制。建议协议加能力协商或按方法粒度的超时表 + 进度事件（0x03 Event 已定义未使用）。
4. **删除语义统一**：本轮 delete_midi 已如实上报、folders/delete 不再清回收站；剩余差异（SyncWorkspaceToProjects 直接删镜像等）建议统一为「删除 = 入回收站 + 凭据 + 失败上报」。
5. **数据写路径的静默失败**：`_ =` 遍布 SaveDraft/manifest/theme 等；「落盘失败=数据丢失」的路径至少应 slog.Error。
6. **引擎 IPC 无鉴权/引擎侧路径校验**（H10）与 Events() 专职读者（H9）：协议级改造，建议立专项。
