# 音频引擎选型与架构方案

> 日期：2026-08-23
> 背景：项目规模扩大后需支持多种声卡驱动（ASIO 等），要求音频引擎高性能、低延迟，
> 后续有 VST 插件兼容开发计划。本文评估候选方案并给出架构建议。

---

## 1. 现状盘点

| 层 | 现状 |
|---|---|
| 应用框架 | Go 1.27 + Wails v2（WebView2 前端 + Go 后端） |
| 音频现状 | 全部走前端 Web Audio：`frontend/js/pianoroll/synth.js`、`soundfont.js`、`frontend/js/arrangement/audio_engine.js`，共享单例 AudioContext |
| 后端音频 | 仅提供音频文件流（`internal/server/handler_arrangement.go`），无原生音频能力 |
| `internal/engine` | 空目录，尚未建立引擎层 |

Web Audio 路线的天花板：
- 无法使用 ASIO / WASAPI 独占模式，延迟受浏览器音频栈限制（Windows 共享模式通常 10~30ms 起步，且不可控）；
- 无法加载 VST 插件；
- 采样率、缓冲区大小、设备切换均不可控；
- 合成/解码在 JS 中执行，多轨高负载时性能受限。

结论：**要支持 ASIO 和 VST，必须引入原生音频引擎，Web Audio 只能作为降级/预览路径。**

---

## 2. 需求拆解

1. **驱动覆盖**：ASIO（专业声卡低延迟）、WASAPI（共享 + 独占）、MME/DirectSound（兜底）；
2. **低延迟实时性**：音频回调线程必须实时安全（无锁、无内存分配、无 GC 停顿风险）；
3. **设备管理**：枚举设备、采样率/缓冲区/控制面板（ASIO Control Panel）、热切换；
4. **合成与混音**：原生 SoundFont 渲染、多轨混音、总线效果（替代/承接现有 JS 合成）；
5. **VST 兼容（后续）**：至少 VST3 宿主（VSTi 为主，可能含效果器），含插件 GUI 嵌入；
6. **稳定性**：插件崩溃不能拖垮主程序。

---

## 3. 候选方案对比

| 方案 | ASIO | WASAPI | VST 宿主 | 设备管理 | 与 Go 集成 | 许可证 | 评价 |
|---|---|---|---|---|---|---|---|
| **JUCE（C++）** | ✅ 成熟 | ✅ | ✅ VST3 成熟（VST2 需旧 SDK） | ✅ AudioDeviceManager 全套 | 需编译为独立进程或 DLL | 免费层 AGPL；商用需付费 | 能力最全，VST 路线事实标准 |
| **PortAudio（C）** | ✅（需 ASIO SDK 编译） | ✅ | ❌ | 中等 | cgo 绑定（gordonklaus/portaudio） | MIT | 只解决 I/O，其余全自研 |
| **miniaudio（C）** | ❌ 无 ASIO | ✅ | ❌ | 简单 | cgo 绑定（gen2brain/malgo），集成最省事 | 公有领域/双许可 | 轻量好用，但**不满足 ASIO 需求** |
| **RtAudio（C++）** | ✅ | ✅ | ❌ | 中等 | 需自写绑定 | MIT | PortAudio 的 C++ 同类，生态略小 |
| **纯手搓（Go/Rust 直写 WASAPI+ASIO）** | 需自行实现 | 需自行实现 | ❌ | 全部自研 | 原生 | 自有 | WASAPI 可控；ASIO 驱动层工作量 2~4 周起，且要处理各家声卡驱动的兼容怪癖 |

关键事实：
- **miniaudio 不支持 ASIO**（后端仅 WASAPI/DirectSound/WinMM 等），直接排除作为主引擎；
- **Go 生态没有任何可用的 VST 宿主方案**（仅有实验性 `pipelined/vst2`，不可用于生产）；
- VST3 宿主的工程复杂度极高（插件生命周期、参数/状态、GUI 嵌入、多进程隔离），业界普遍依赖 JUCE 的 `AudioPluginFormat` / `AudioProcessorGraph`，手搓不现实；
- ASIO 驱动层可以手搓（Steinberg ASIO SDK 免费），但"各家声卡驱动兼容性"是长期维护成本，JUCE/PortAudio 已替你踩完这些坑。

## 4. JUCE 重点评估

**能力匹配度：几乎满分。** ASIO/WASAPI/MME/DirectSound 全覆盖、AudioDeviceManager 自带设备枚举/采样率/缓冲区/ASIO 控制面板、VST3 宿主成熟、AudioProcessorGraph 可做效果链路由、SoundFont/采样合成有现成模块。JUCE 8 在 Windows 上还大幅优化了渲染与底层性能。

**许可证与成本（2026-08-23 修订）：**
- JUCE 8 已取消 AGPL 开源选项，全部许可层级均为商业 EULA；免费档为 Starter（面向低收入开发者，含收入上限约束）。本节旧版所载"AGPLv3 免费层 / Indie 约 $800"为 JUCE 7 时代信息，**已作废**；
- 权威结论与合规要点统一见《JUCE音频引擎开发计划》第 9 节；具体收入门槛数字以官网现行条款为准，快照存档于 `docs/licenses/`。对商业产品而言，许可费用远低于手搓数月的研发成本；
- 参考：https://juce.com/legal/juce-8-licence/

**与 Go 的集成：不要试图 cgo 直接绑定整个 JUCE**（构建体系、C++ 模板、线程模型都会让 cgo 极其痛苦）。正确姿势是**独立子进程**，见下节。

**JUCE 的短板：** 库体积大、C++ 构建链（CMake/Projucer）引入新的工具链依赖；团队若无 C++ 经验有学习成本。

## 5. 推荐架构：Go 主进程 + 原生音频引擎子进程

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  AI_MIDI.exe (Go + Wails)   │        │  aimidi-engine.exe (原生引擎) │
│  - UI / AI / 项目管理        │  IPC   │  - 设备管理 (ASIO/WASAPI)     │
│  - MIDI 编辑、编排逻辑       │◄─────►│  - 合成器 / SoundFont 渲染    │
│  - 引擎抽象接口 (internal/  │ 命名   │  - 混音器 / 效果链            │
│    engine，纯 Go 接口)      │ 管道   │  - VST3 宿主（后续）          │
└─────────────────────────────┘        └──────────────────────────────┘
```

要点：
1. **音频样本永远不进 Go 进程**。Go 侧只发命令（NoteOn/Off、走带、加载音色、设备切换），引擎侧独占音频线程。Go 的 GC STW 会冻结所有线程，音频回调放在 Go 进程内做低延迟是不可接受的——子进程方案从根上消除这个问题。
2. **IPC 用 Windows 命名管道**（低延迟、双向、原生支持），协议细节以《引擎IPC协议》（`docs/引擎IPC协议.md`）为准：控制消息用 JSON（可读易调试），高频消息（MIDI 事件/timecode）用紧凑二进制，大块数据（音色库加载）走文件路径传递。
3. **崩溃隔离**：VST 插件崩溃是常态（业界如 Bitwig 也采用多进程插件架构）。引擎子进程崩溃后 Go 侧可自动重启并恢复会话状态，主程序不死。后续做 VST 时还可再加一层"每插件一进程"。
4. **接口先行**：`internal/engine` 先定义纯 Go 接口（`DeviceManager` / `SynthEngine` / `MixerBus` / `PluginHost`），IPC 只是其中一种实现。这样：
   - 第一阶段可以先用简单实现（甚至保留 Web Audio 后端）顶上；
   - 引擎进程内部从 PortAudio 换成 JUCE、或加 VST 模块，Go 侧零改动。
5. **时钟基准**：以引擎的采样点位置为主时钟，前端 JS 通过轮询/推送 timecode 跟随（替代现在以 AudioContext 时钟为锚的调度），保证 UI 播放头与声音严格同步。

## 6. VST 兼容路线与许可证须知

| 事项 | 说明 |
|---|---|
| **VST3（推荐）** | Steinberg vst3sdk 双许可：GPLv3 或免费的 Steinberg 专有许可（需签署）。用 JUCE 宿主时由 JUCE 封装大部分细节，仅需按 JUCE 要求配置 SDK 路径 |
| **VST2（谨慎）** | Steinberg 已于 2018 年停止分发 VST2 SDK，新产品**无法合法获取** VST2 开发授权；除非已有历史授权，否则不建议承诺 VST2 兼容，对外只承诺 VST3 |
| **ASIO** | ASIO SDK 免费（需接受 Steinberg 许可条款）；"ASIO" 名称/标识的使用需遵守其品牌条款 |
| **插件分发** | 宿主只加载用户自有的插件，不分发插件本体，一般不产生额外授权问题 |

## 7. 分阶段路线图

**阶段一（立刻可做，不依赖选型定案）**
- 在 `internal/engine` 定义引擎抽象接口 + IPC 协议草案；
- 保持 Web Audio 现状作为预览路径。

**阶段二（引擎进程落地）**
- 搭建引擎子进程骨架：命名管道协议、进程生命周期管理（启动/心跳/崩溃重启）；
- 驱动层先用 **PortAudio**（含 ASIO）或直接用 **JUCE AudioDeviceManager** 起步；
- 把 SoundFont 渲染、多轨混音从 JS 迁到引擎进程。

**阶段三（VST）**
- 引擎内接入 JUCE 插件宿主（VST3）；
- 插件 GUI 通过 HWND 嵌入 Wails 窗口（或独立弹出窗口，实现更简单）；
- 插件参数面板由前端 UI 渲染（通过 IPC 同步参数元数据），原生 GUI 仅作为备选。

**选型建议一句话：若 VST 计划是确定的，直接从 JUCE 起步**——驱动层、设备管理、VST 宿主一次到位，避免先手搓再推倒重来；若近期只想先把低延迟播放做出来、VST 还可能变卦，可先用 PortAudio 做驱动层过渡，但引擎进程骨架和接口要按最终能装下 JUCE/VST 来设计。

---

## 附：不推荐的路线

- **cgo 绑定 JUCE 进 Go 主进程**：构建与线程模型双重灾难；
- **cgo + PortAudio 直接在 Go 内做音频回调**：GC 停顿在 128 samples 以下缓冲区极易爆音；
- **miniaudio 作主引擎**：无 ASIO；
- **继续加码 Web Audio**：天花板已到，投入越大迁移成本越高。
