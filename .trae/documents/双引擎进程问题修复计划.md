# 双音频引擎进程问题修复计划

> 日期：2026-08-24 ｜ 触发：用户发现「一次启动出现两个音频引擎」

---

## 一、现场证据（实测捕获）

当前系统**活捉现场**——两个孤儿引擎进程，主程序已退出：

```
PID 17672  启动于 16:52:17  D:\pyx\AI_MIDI-go\bin\aimidi-engine.exe
PID 21488  启动于 16:52:29  D:\pyx\AI_MIDI-go\bin\aimidi-engine.exe
（AI_MIDI 主进程：不存在）
```

## 二、根因分析

### 事实链

1. 主程序单实例锁可靠（[dialogs_windows.go:43](file:///d:/pyx/AI_MIDI-go/internal/app/dialogs_windows.go#L43) `Local\` 互斥体 + ERROR_ALREADY_EXISTS），**不存在两个主程序**；
2. supervisor 每次 `runOnce` 只拉一个引擎、`Start()` 幂等（[supervisor.go](file:///d:/pyx/AI_MIDI-go/internal/engine/supervisor.go)）；
3. **两个引擎是两次独立的主程序启动各拉起一个**（间隔 12 秒 = 用户快速重启应用），主程序退出后**都没被回收**；
4. 主程序正常退出走 `defer engineSup.Stop()` → shutdown 引擎；**主程序被强杀/崩溃时 defer 不执行**，唯一兜底是 Job Object——而当前两个孤儿证明 **Job 兜底失效**。

### 两个独立缺陷

| # | 缺陷 | 机理 |
|---|---|---|
| **A. 孤儿引擎（主因）** | 主程序异常退出后引擎不陪葬 | ① Job Object 挂靠全程**静默失败**：[job_windows.go](file:///d:/pyx/AI_MIDI-go/internal/engine/job_windows.go) 中 `ensureEngineJob` 的 `SetInformationJobObject` 失败仅 return（jobHandle 恒 0），`attachProcessToJob` 的 `OpenProcess`/`AssignProcessToJobObject` 失败也静默——主程序若嵌套在某 Job（Windows Terminal/IDE 启动）时 Assign 可被拒；② 引擎自身无任何「主人还活着吗」的感知，管道断开也只会回监听等重连（设计为守护器重连），主人死了就永远挂着占声卡 |
| **B. 双开叠加** | 孤儿残留 + 新启动拉新引擎 = 用户看到两个 | 孤儿引擎占着声卡/设备，用户感知「启动了两个」；且旧孤儿与新引擎并发操作同一音频设备会再诱发设备争抢问题 |

辅助放大因素：Dial 失败路径 `_ = cmd.Process.Kill()` 丢弃错误、`<-waitCh` 无超时上限（极端卡死会冻结守护循环）。

## 三、修复方案（防御纵深三层 + 诊断）

### 1. 引擎父进程看门狗（根治孤儿——核心修复）

**文件**：[engine/Source/Main.cpp](file:///d:/pyx/AI_MIDI-go/engine/Source/Main.cpp)、[internal/engine/supervisor.go](file:///d:/pyx/AI_MIDI-go/internal/engine/supervisor.go)

- supervisor `runOnce` 拉起引擎时传父进程 PID：`exec.Command(s.exePath, "--parent", strconv.Itoa(os.Getpid()))`；
- 引擎 `main(int argc, char** argv)` 解析 `--parent <pid>`：
  - `OpenProcess(SYNCHRONIZE, FALSE, parentPid)`——若**打开失败**（父已死）直接 `return 0`；
  - 成功则持有句柄，起看门狗线程：`WaitForSingleObject(hParent, 2000)` 循环，`WAIT_OBJECT_0`（父进程终止，句柄信号态**免疫 PID 复用**）→ `juce::MessageManager::callAsync([]{ ...stopDispatchLoop(); })` 优雅退出；
  - 无 `--parent` 参数（手动调试运行）→ 跳过看门狗，行为不变。

### 2. 主程序启动清场（收割历史孤儿 + 未知路径孤儿）

**文件**：[internal/engine/supervisor.go](file:///d:/pyx/AI_MIDI-go/internal/engine/supervisor.go)（或新文件 `cleanup_windows.go`）

- supervisor `Start()` 首步：用 `windows.CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS)` 枚举进程，凡镜像名为 `aimidi-engine.exe` 且 PID ≠ 本会话当前子进程 → `OpenProcess(PROCESS_TERMINATE)` + `TerminateProcess`，每个杀掉的记 `slog.Info("[engine] 清理残留引擎进程", "pid", ...)`；
- 引擎是主程序专属附属进程（闭源、无手动长开场景），清场语义安全；
- 这一步立即解决当前系统里的两个孤儿（实施时第一步先手动清一次验证）。

### 3. 引擎单实例互斥体（最后防线，防任何未来逻辑失误双开）

**文件**：[engine/Source/Main.cpp](file:///d:/pyx/AI_MIDI-go/engine/Source/Main.cpp)

- `main` 最早处：`CreateMutexW(NULL, FALSE, L"Local\\AI_MIDI_ENGINE_Singleton")`，`GetLastError() == ERROR_ALREADY_EXISTS` → `fprintf(stderr, "[aimidi-engine] 已有实例运行，退出\n")` 并 `return 0`；
- 与方案 1/2 配合后时序安全：清场 + 看门狗保证启动前无存活引擎，互斥体必然可得；若极端竞态下仍双开，后启动者自动退位，守护器 Dial 其管道失败即触发既有重启逻辑（清场会再兜底）。

### 4. Job Object 失败可观测（不修行为，修可见性）

**文件**：[internal/engine/job_windows.go](file:///d:/pyx/AI_MIDI-go/internal/engine/job_windows.go)

- `ensureEngineJob`：`SetInformationJobObject` 失败时 `slog.Warn("[engine] Job Object 创建/配置失败，孤儿兜底降级为父进程看门狗")`（仅一次）；
- `attachProcessToJob`：`OpenProcess`/`AssignProcessToJobObject` 失败时 `slog.Warn`（含引擎 PID 与错误码）；
- 看门狗上线后 Job 只是第一层兜底，失败不再致命。

### 5. runOnce Dial 失败路径加固

**文件**：[internal/engine/supervisor.go](file:///d:/pyx/AI_MIDI-go/internal/engine/supervisor.go)

- `_ = cmd.Process.Kill()` 改为记录错误：`if err := cmd.Process.Kill(); err != nil { slog.Warn(...) }`；
- `<-waitCh` 加 5 秒上限：超时后再次 `Kill` 并 `slog.Warn`（进程若仍卡内核态，由 Job/看门狗最终收割），守护循环不再可能被单点冻结。

## 四、关键决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 孤儿检测方式 | **父进程句柄 WaitForSingleObject**（非轮询 OpenProcess 父 PID） | 句柄信号态免疫 PID 复用误判；一次 OpenProcess 持有即可 |
| 引擎退出方式 | 看门狗触发 `stopDispatchLoop` 优雅退出 | 走既有 shutdown 路径，音频设备干净释放 |
| 清场时机 | supervisor `Start()` 首步（拉引擎之前） | 保证新引擎启动时设备与互斥体均空闲 |
| 互斥体命名空间 | `Local\` | 引擎与主程序同会话；无需跨会话（无服务/多用户场景） |
| 旧引擎兼容 | 无 `--parent` 时跳过看门狗 | 手动运行引擎调试不受影响；存量孤儿靠清场收割 |

## 五、验证步骤

1. **清场验证**：手动终止当前两个孤儿 → 启动应用（浏览器模式）→ 日志无「清理残留」、任务管理器仅一个 aimidi-engine.exe、`/api/audio/status` ready。
2. **看门狗验证**：任务管理器**强杀** AI_MIDI 主进程 → 引擎应在 ~2 秒内自行退出（`Get-Process aimidi-engine` 连续观察）；stderr 可见优雅 shutdown 日志。
3. **双开防线验证**：手动直接双开 `bin\aimidi-engine.exe` → 第二个实例立即退出；应用内崩溃重启（杀引擎进程）→ supervisor 拉起新引擎 → 仍只有一个。
4. **快速重启验证**：启动应用 → 5 秒内强杀主程序 → 立即再启动 → 全程任务管理器观察，任意时刻 ≤1 个引擎进程。
5. **回归**：`go build/vet/test` 全绿；冒烟测试全过（engine_smoke）；Web Audio 自测页 pass。
6. **打包**：`wails build` → 复制 `AI_MIDI.exe`，交付用户复测。
