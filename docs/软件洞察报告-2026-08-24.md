## 1. 执行摘要

### 1.1 九维评分卡（1–5 分，5 为专业级）

| 维度 | 得分 | 竞品基准 | 一句话判词 |
|---|---|---|---|
| 核心功能完整度 | 3.5 | Suno Studio 2.0 ≈ 4.5 | 对话→MIDI→精编→编曲→试听闭环完整，缺音频导出/混音/自动化 |
| 信息架构与导航 | **2.0** | FL Studio ≈ 4.5 | 三页 MPA 割裂 + 双 AI 入口并存，桌面应用整页跳转属结构性硬伤 |
| 编辑器交互效率 | 4.0 | FL Studio ≈ 5 | 两编辑器各自忠实对齐 FL 惯例；钢琴窗 Shift+拖拽克隆、Alt 临时禁吸附、力度 lane、双击属性面板均已实现（v1.2 核实，见附录 D） |
| 视觉专业度 | 3.5 | Studio One ≈ 4.5 | 图纸拟物语言执行高度自洽（见《前端设计必读.md》哲学），token 体系健全；代价是信息密度与扫描效率，属"风格 vs 效率"的权衡而非失控 |
| 反馈与状态可见性 | 3.5 | — | 自动保存状态章/HUD/toast 是亮点；index 页纯文字 console 弱 |
| 错误预防与恢复 | 3.0 | — | 撤销/自动保存/原子写配置扎实；后端错误上下文丢失、panic 防护面窄 |
| 前端工程质量 | **2.0** | K.G.Studio（开源）≈ 3.5 | 无构建、无模块、无测试；chat.js 单文件 137KB 全局脚本 |
| 后端工程质量 | 3.5 | — | 模块边界清晰、IPC 超时完备、路径安全；全局可变状态多、错误响应不一致 |
| 工程化成熟度 | **1.5** | 企业级 ≈ 4 | 无 CI、无自动更新、无崩溃上报、日志裸用、API Key 明文存储 |

**综合：2.9 / 5 —— 一个功能内核超出平均水准、外壳（架构呈现 + 工程化）拖后腿的产品。**

### 1.2 Top 10 发现（按影响排序）

1. **三页 MPA 是最大的体验债**：`index.html` / `chat.html` / `settings.html` 整页 `<a href>` 跳转，主题切换需在每页 head 注入防闪烁脚本（`frontend/index.html:5-14`、`frontend/chat.html:5-14`、`frontend/settings.html:5-14` 三份重复），导航方向靠 `sessionStorage` 传递（三页各一份 `:20-29`）。这是 2026 年桌面应用的逆向架构——Wails 本身就是单窗口 WebView，天然适合 SPA。
2. **双 AI 入口互相稀释**：`index.html`（快捷操作，单次任务）与 `chat.html`（档案库+对话工作台）是两套并存的 AI 调用面，功能重叠但体验割裂；2026-08-22 报告"未做/建议"第 7 条已指出此产品决策悬而未决。
3. **（v1.2 撤回）钢琴窗 FL 惯例缺口**：初版 v1.1 称钢琴窗缺"Shift+拖拽复制 / Alt 临时禁吸附 / 力度 lane / 音符属性面板"，经复核**四项全部已实现**——Shift+拖拽克隆（`pianoroll.js:1770-1789`，注释明写"克隆复制音符"）、Alt 按下时 freeSnap 启用（`pianoroll.js:1782/1947/1952`）、可拖拽绘制的力度 lane（`pianoroll.js:1559-1571`，双击还出力度缩放弹窗）、双击音符属性面板（`pianoroll.js:1853/2746`）。钢琴窗右键=擦除与编曲窗右键菜单亦各自忠实复刻 FL 对应编辑器惯例。编辑器交互层无真实缺口。
4. **前端零测试 + 无构建链**：`frontend/js/` 无任何测试；`chat.js` 137KB、`pianoroll.js` 115KB、`arrange.js` 101KB 为 IIFE 全局脚本，靠 `<script defer>` 顺序加载（chat.html 加载 14 个脚本）。2026-08-22 报告第一轮缺陷 #1（arrange.js IIFE 丢实参导致整窗瘫痪）正是这种组织方式的直接产物。
5. **错误信息在生产链路上蒸发**：创建项目失败只返回 `"创建项目失败"`（`internal/server/handler_project.go:24-44`），不携带 err；同文件 `:100-112` 却直接 `err.Error()`——两套风格并存。`internal/server/handler_midi.go:82-174` 的 LLM 失败只给"调用失败，请稍后重试"。用户报障时无法自诊断，开发者无法远程定位。
6. **panic 防护几乎为零**：全后端仅 1 处 `recover()`（`internal/tasks/driver.go:11`）。HTTP/SSE handler 无恢复中间件——2026-08-22 报告问题一 #8（坏历史 panic SSE 协程）证明这类风险真实存在，修的是个案而非类别。
7. **API Key 明文落盘**：`internal/config/settings.go:170-202` 原子写入 `settings.json`（0644 权限），密钥明文。GET 脱敏（已修复项）只防了传输层，没防磁盘层。企业级做法是 Windows DPAPI / Credential Manager。
8. **图纸拟物语言的一致性高，但可读性代价未被审视**：①②③ 编号站、stamp 印章、等宽大写按钮、网格底纹共同构成《前端设计必读.md》"工程图纸/技术蓝图"的刻意设计语言，执行自洽、有辨识度；但全大写 + letter-spacing 的按钮文案（`style.css:190-209`）与恒定存在的装饰层客观上降低扫描效率——这是风格与效率的权衡点，值得用可读性数据审视而非全盘推翻（详见 §5）。
9. **双音频路径无统一状态机**：Web Audio（`frontend/js/pianoroll/synth.js:104-164`）与原生引擎（`frontend/js/engine/engine_bridge.js`、`frontend/js/arrangement/audio_engine.js:149-179`）按 `auto/webaudio` 开关分支（`synth.js:57-79`），编曲窗内 SF2 走原生、非 SF2 强制 Web Audio——两条时间轴、两套增益语义，用户听到的是"哪个引擎在响"的抽奖结果。
10. **无 CI / 无自动更新 / 无崩溃上报**：仓库无 `.github/workflows`，构建靠 `tools/*.bat` 手动脚本（且 `quick_build.bat`、`RUN.bat`、`启动.bat` 三个入口并存）；仓库根目录残留 `e2e_run.log`、`eng_out.log`、`crash_probe.ps1` 调试产物。用户侧出问题只能靠口头描述复现。

### 1.3 一句话结论

**AI_MIDI 拥有市面上稀缺的"本地优先 + 对话式 + 完整钢琴卷帘"内核（详见 §3 定位分析），当前形态是一个功能 3.5 分、外壳 2 分的产品；按 §9 路线图执行 P0+P1 后，有实力成为 4 分以上的专业工具。**

## 2. 产品定位与核心工作流

### 2.1 这是什么软件

- **形态**：Wails v2 桌面应用（Go 后端 + WebView 前端 + JUCE 原生音频引擎子进程，命名管道 IPC）
- **核心主张**：用多轮对话驱动 AI 生成/修改 MIDI，在应用内完成钢琴卷帘精编、多轨编曲、SF2 试听，全流程数据本地化
- **架构事实**（`main.go:32-130`）：支持 Wails 原生窗口与 `-browser` 浏览器双模式；单实例保护、Splash、引擎 supervisor 全局注册

### 2.2 用户旅程与断点标注

```
首次启动 ──→ 配置 API Key ──→ 新建档案 ──→ 对话生成 MIDI ──→ 试听 ──→ 钢琴窗精编 ──→ 编曲窗编排 ──→ 导出
   │              │                │              │             │            │              │           │
   ▼              ▼                ▼              ▼             ▼            ▼              ▼           ▼
 [OK]          [断点1]          [OK]          [OK,强]       [断点2]      [OK,强]        [断点3]     [断点4]
              设置页独立      档案库+API横幅   SSE流式+      新MIDI链     FL式快捷键      编曲窗与    只有 MIDI
              成一页(跳页)    (chat.html:58)  提问卡片       toast跳转    +自动保存章     对话窗折叠  下载，无
              无连通引导                     (修复于0822)               (0822修复)     切换，学习  WAV/分轨
                                                                                     成本高      导出
```

- **断点 1**：首次启动落在 `index.html`（快捷操作），未配置 Key 时该页无任何引导（API 横幅只在 chat.html）；用户要先发现"多轮对话"按钮才知道去哪配置。
- **断点 2**：生成完成只有 toast + 底部小链接（`chat.html:178`），没有"立即在钢琴窗打开"的一步直达（侧栏提示"双击打开"是 0822 补的，仍依赖发现性）。
- **断点 3**：对话面板与编曲窗是折叠舞台叠放（`chat.html:98-101` `arr-stage`），钢琴窗又是底部抽屉——三层空间嵌套，新用户要建立"我现在在哪一层"的心智模型。
- **断点 4**：作为编曲软件，终点只有 `.mid` 下载。竞品（Suno Studio 2.0、网易天音、Mureka）音频/分轨导出已是标配（见 §3.2）。

## 3. 竞品对标（2026-08 调研）

### 3.1 三类竞品格局

**A. AI 生成工具（prompt→成品，编辑浅）**
- Suno v5.5 / **Studio 2.0**（2026-08）：从 prompt 生成器进化为完整 DAW——MIDI 时间轴、钢琴卷帘（音高/力度/调制）、Musical Typing、波表合成器、分轨分离、自动化曲线、Chat Bar 对话式设计插件。Premier 订阅制，推荐 Chrome（来源：suno.com/blog/studio-2，thenextgentechinsider.com 2026-08-15）
- Udio：强在人声歌曲与 inpainting 局部重绘，无 MIDI 导出，编辑止步于段落扩展
- AIVA：古典/影视配乐向，**MIDI + WAV 导出、乐谱级编辑**，与 AI_MIDI 定位最接近
- 国内：网易天音（词曲编唱混发全链路 + MIDI 分轨导出）、Mureka V9（MIDI 导出、局部重生成、MusiCoT）、海绵音乐（字节）、蘑兔/MELO（多模态输入）

**B. 传统 DAW（编辑深，无 AI 原生）**
- FL Studio / Studio One / Ableton / Cubase：钢琴卷帘交互的事实标准制定者。FL 惯例：中键拖拽平移、右键删除、`Ctrl+B` 向右复制、`Alt+拖拽` 克隆、`Alt+滚轮` 力度、按住 `Alt` 临时禁用吸附、全场景右键菜单、工具菜单（量化/切分/粘合/琶音/扫弦/随机化）（来源：image-line.com 官方手册）

**C. AI+DAW 融合态（AI_MIDI 的直接赛道）**
- WavTool：浏览器 DAW + Conductor 对话助手（生成 MIDI、转写、和弦建议、直接操纵参数）（来源：aitoolsatlas.ai）
- K.G.Studio（开源）：浏览器 DAW + Tone.js + 项目感知 AI agent——**工具执行确认、agent todo 卡片、上下文自动压缩、按项目持久化会话、4 语言 i18n**（来源：github.com/KGAudioLab/K.G.Studio）。其 2026-06 的 agent 能力清单（轨道管理工具、全局轨道读写、写操作确认）与本产品的 MCP 工具体系高度同构，是最精确的镜像竞品。

### 3.2 能力矩阵

| 能力 | AI_MIDI | Suno Studio 2.0 | WavTool / K.G.Studio | FL Studio | 网易天音 / Mureka |
|---|---|---|---|---|---|
| 对话式生成 MIDI | ✅ | ✅（Chat Bar） | ✅ | ❌ | 部分 |
| 钢琴卷帘精编 | ✅ | ✅ | ✅ | ✅（标杆） | ❌ |
| 多轨编曲窗 | ✅ | ✅ | ✅ | ✅ | 有限 |
| 本地优先/数据自主 | ✅（唯一） | ❌ 云 | ❌ 云 | ✅ | ❌ 云 |
| 离线可用 | 部分（LLM 需网） | ❌ | ❌ | ✅ | ❌ |
| WAV/分轨导出 | ❌ | ✅ | ✅ | ✅ | ✅ |
| 混音器/自动化 | ❌（Mixer 未接线） | ✅ | 部分 | ✅ | ❌ |
| 自动更新/崩溃上报 | ❌ | 平台托管 | 平台托管 | ✅ | 平台托管 |

### 3.3 定位结论

**AI_MIDI 的差异化护城河 = "本地桌面 + 对话式 AI + 专业钢琴卷帘"三者交集，市面上没有第二个。** 这个定位恰好避开与 Suno（云、人声歌曲）和 FL（无 AI、高门槛）的正面竞争，服务"想要 AI 起步、但要求精编控制权和数据隐私"的用户。当前问题是：**外壳（MPA、视觉装饰、工程化）没有配得上这个定位的专业感**，且缺 WAV 导出这一"最后一公里"（编完曲只能拿走 MIDI，等于把混音收益让给用户自己的 DAW——也行，但要明说这是设计而非缺失）。

## 4. UX 洞察（按旅程阶段）

### 4.1 导航与信息架构

| 问题 | 证据 | 严重度 |
|---|---|---|
| 整页跳转丢失状态：钢琴窗抽屉高度、编曲窗折叠态等 localStorage 项在跳页后要整页重载恢复 | `frontend/chat.html:5-29`（防闪烁 + nav-dir hack 三份） | 高 |
| 设置是独立页面而非抽屉/弹窗：改一个参数（如 BPM 预填、模型）要离开工作台跳页再跳回 | `frontend/settings.html` 全页；对话中 `MODEL: --` stamp 只展示不可点（`chat.html:86`） | 高 |
| 首启落点错误：`index.html` 无 API 引导（横幅只在 chat.html:58-62） | `frontend/index.html` 全文 | 高（新用户流失点） |

### 4.2 操作负担与冗余

- **危险操作确认已统一**（0822 修复），`showConfirm` 是自定义弹窗带焦点还原与 Esc 分层（`frontend/js/chat.js:2424-2456`）——这点做对了。
- **上传按钮五连排**：`chat.html:111-117` 上传/下载/文件夹/删除/撤销五个按钮等权重平铺，高频（上传）与高危（删除）无视觉区分；专业软件惯例是主操作显性、危险操作收进 `⋯` 菜单。
- **任务切换条**：下拉 + 独立"重命名"按钮（`chat.html:150-153`），双击下拉项重命名是更自然的惯例。
- **编曲窗与对话窗切换**是单按钮折叠（`chat.html:89`），无键盘快捷键、无记住上次状态（有 localStorage 但切换动画 800ms 每次重播）。

### 4.3 编辑器交互（钢琴窗 vs 编曲窗一致性）

**已有的好底子（经复核：与 FL 惯例的对齐度比初版报告评估的更高）**：钢琴窗快捷键表（`pianoroll.js:2279-2418`）覆盖 Ctrl+Z/Y/C/V/X/B、Alt+X/S/A/R/Y（力度缩放/静音/全选/随机化/翻转——FL 同款语义）、Ctrl+Q 量化；滚轮体系（Ctrl 缩放 / Shift 微移 / Alt 力度，`pianoroll.js:1493-1556`）与 FL 对齐；中键/Shift+右键平移（`pianoroll.js:1613-1694`）。**右键=擦除正是 FL 钢琴卷帘的原生惯例**（image-line 官方手册：右键删除音符），编曲窗的轨道头/Clip/空白三分右键菜单（`arrange.js:772-811`）与 Alt+拖拽克隆（`arrange.js:960-981`，代码注释自称"FL 式复制"）也各自对应 FL Playlist 的行为——**两编辑器的交互语言并非割裂，而是分别继承了 FL 两个编辑器的惯例**。初版报告对此的"不一致"批评有误，已修正。

**缺口**（v1.2 全量复核后：以下四项**均已实现**，初版缺口表全部撤回）：

### 4.4 反馈与状态

- **亮点**：钢琴窗自动保存状态章 `EDIT…/SAVING/SAVED/SAVE ERR` + 失败 toast + 关签脏检查（`pianoroll.js:514-604`，0822 修复）；编曲窗 HUD 徽章（`chat.html:252`）；任务轮询自适应 2s/10s 降载（`frontend/js/tasks.js:10-12`）。
- **弱项**：`index.html` 结果区是纯文字 console 行（`index.html:117-119`），无进度条、无耗时统计、无可复制日志；AI 生成期间无预计时长提示（LLM 流式首字延迟可达 10s+，竞品普遍有骨架屏/打字指示）。
- SSE 封装本身有超时与 AbortController（`frontend/js/app.js:150-220`），工程上合格。

### 4.5 错误预防与恢复

- 撤销/重做：钢琴窗、编曲窗均有（0822 修复了快照时序类 bug 四处）；跨编辑器的全局撤销（如"撤销 AI 生成"）不存在——对话生成不可回滚到一个动作，只能靠消息编辑模式（`chat.html:166-170` 编辑撤回条，好设计）。
- 自动保存防抖 800ms + sendBeacon 兜底（0822）已达标。
- **上传无类型/大小预校验提示**：`accept=".mid,.midi"` 只过滤选择器，拖入错误文件的行为未见友好提示（dropzone `index.html:49-54` 与 chat 上传共用 `uploadInput`）。

### 4.6 首次使用引导

- API 横幅 + deep-link 去设置（0822 修复，`chat.html:58-62`）是唯一引导。无示例项目、无 30 秒上手 tour、无"试试这个 prompt"的种子内容——对一个依赖用户自备 API Key 的工具，空态转化率是生死线。竞品 K.G.Studio 开箱即用（内置 demo），Suno 免注册试用。

## 5. 视觉设计评估

### 5.1 做对的

- **设计 token 体系**：双主题（暗夜蓝 `style.css:6-34` / 暖纸 `:36-63`）变量完整覆盖背景/描边/网格/危险色/HUD，0822 还补齐了缺失的 `--color-bg-alt`——这是超过多数独立软件的工程化视觉管理。
- **动效规范文档化**：`前端设计必读.md` 定义贝塞尔曲线族、时长层级、"仅 transform/opacity"、reduced-motion 降级——罕见的专业程度。
- **风格自洽**：《必读》明文"Q 弹、有重量、有温度"的物理动效哲学 + "工程图纸/技术蓝图"视觉概念（`style.css:1-3`），从 token 到动效到装饰语言执行一致，产品有可识别的身份——这恰恰是多数独立软件缺的。
- **无障碍有局部投入**：`:focus-visible`（`style.css:104-107`）、弹窗焦点还原（`chat.js:2440-2447`）、Esc 分层（0822）。

### 5.2 与专业 DAW 视觉语言的差异（经复核：是"权衡"而非"失控"）

> 初版将下表定位为"差距/缺陷"，复核后修正为**刻意的设计权衡**：色彩克制度、装饰密度、默认主题均源自《前端设计必读.md》与蓝图概念的产品身份选择。表中保留的是客观差异事实 + 权衡代价，供决策参考，不再作为"必须改"的判断。

| 维度 | 专业 DAW 惯例 | AI_MIDI 的选择（初衷） | 权衡代价 |
|---|---|---|---|
| 色彩克制度 | 90% 中性灰阶，彩色只用于状态/选中/录制 | 主色蓝青 + 高饱和橙主按钮 + 3D 硬阴影（`style.css:15-22/216-233`），《必读》"有重量"哲学的体现 | 高饱和橙色大面积使用时，状态色（录制红/危险红）的区分度被压缩 |
| 文本可读性 | 正文用 UI 字体，等宽只用于数值/时间码 | 按钮/标签全等宽 + 全大写 + letter-spacing（`style.css:190-209`），图纸标注语言 | 全大写中文按钮无影响；英文 stamp 的扫描速度客观慢于大小写混合（人因工程共识） |
| 装饰密度 | 装饰为零，每个像素承载信息 | 图纸网格底纹（`style.css:87-97`）+ stamp 印章 + 拟物装饰，蓝图氛围的组成部分 | 恒定视觉噪音；低对比内容叠加底纹时可读性下降 |
| 信息密度 | DAW 用户要求高密度（轨道行高 60-72px 内塞满控件） | 卡片化 + 大留白（`chat.html:101-183` 三栏） | 一屏容纳的功能少于 FL/Studio One；高频用户滚动/切换成本上升 |
| 深浅主题策略 | 专业工具默认深色 | 默认暖纸浅色（`index.html:2`） | 长时间盯屏疲劳、色彩感知偏差（音频工作者的常见偏好是深色） |

### 5.3 改造方向（尊重蓝图书身份的前提下的微调建议）

> 原则修正：初版建议"默认深色、删 3D 硬阴影、橙色退位"实质是推翻产品视觉身份，**撤回**。以下仅保留与初衷兼容的增量优化：

1. **主题记忆优先**：默认主题维持暖纸（产品身份），但首次检测到系统 `prefers-color-scheme: dark` 时询问一次而非直接切换。
2. **状态色保护**：录制红/危险红使用场景周围避免大面积高饱和橙，保证状态一眼可辨（微调 `--color-accent` 使用密度，不动按钮体系）。
3. **等宽字体聚焦**：数值/时间码/stamp 维持等宽（图纸标注语言核心）；仅长文案（错误详情、帮助文本）确保用 UI 字体——现状基本已如此，属确认而非改动。
4. **底纹分层**：画布/工作区保留网格底纹（蓝图的"纸"），弹窗/输入框内不叠底纹（现状已有部分隔离）——检查残余叠加点即可。
5. **stamp 双轨**：状态 stamp（REC/SAVED/OFFLINE）保留强样式；装饰性 stamp（SEARCH/ARRANGE）可降为纯文本标签，让"盖章"动作留给真正重要的状态。

- 第二步（P1）：三页合一为 SPA（hash 路由即可），防闪烁脚本、nav-dir hack、顶栏重复按钮全部消失。
- 第三步（P2）：对 pianoroll 的纯逻辑（快照、选中、量化、吸附）抽离为可测模块，配 Vitest。

## 10. 结论

AI_MIDI 站在一个市面空白的定位上（本地优先 + 对话式 AI + 专业钢琴卷帘），内核能力（IPC 纪律、进程治理、编辑器快捷键体系、力度 lane/属性面板/拖拽克隆等 FL 惯例全集、自动保存状态机）已具专业工具的骨架，且"工程图纸"视觉身份与《前端设计必读.md》的动效哲学执行自洽——**这是产品资产，不是负债**。当前与专业软件的真正差距集中在两件事：**① 信息架构（MPA/双入口）拖累体验；② 工程化（CI/日志/错误链路/更新）停留在个人项目形态。** P0 剩余项（均为工程加固，不动产品身份）可在数天内完成；P1 的 SPA 化与模块化是"用起来是专业软件"的决定性投入——视觉只需微调，无需推翻。
